## 1. 通用约定

### 1.1 地址与前缀

| 项 | 值 |
| --- | --- |
| 站点根 | `https://jwgl.med.stu.edu.cn` |
| SPA 入口 | `/app/index.html`（`assetsPublicPath = "/app"`） |
| API 前缀 | **`/dev-api/`**（axios `baseURL`），业务路径再拼 `/appapi/...` |
| 完整形如 | `https://jwgl.med.stu.edu.cn/dev-api/appapi/Studentkb/index` |
| 另一个 axios 实例 | `baseURL = "/mt-api/"`，拦截器与 `/dev-api/` 完全一致；**在前端代码里没有找到实际调用点**（推测为移动端/H5 预留），可忽略 |
| 删除确认 | `/appapi/getIstoken`、`/appapi/Studentkb/index` 在 **去掉 `/dev-api` 前缀后返回 404**，说明前缀是硬性的 |

### 1.2 请求头

前端对两个实例都设了全局默认：

```js
axios.defaults.headers["Content-Type"] = "application/json;charset=utf-8";
const p = axios.create({ baseURL: "/dev-api/", timeout: 50000 });
p.interceptors.request.use(cfg => {
  const skip = (cfg.headers || {}).isToken === false;   // 显式 isToken:false 可跳过
  if (localStorage.getItem("Token") && !skip) cfg.headers.token = localStorage.getItem("Token");
  return cfg;
});
```

- 鉴权头名就是 **`token`**（小写，不是 `Authorization`、不是 `Bearer`）。
- 前端从不发 Cookie 鉴权；实测服务端也**不要求** Cookie。
- 想要不带头，就在请求里带 `isToken: false`（前端作用域，服务端不认这个字段）。

### 1.3 响应封装（重要，和常见约定不同）

**HTTP 状态码恒为 200**，业务状态在 body 的 `code` 里：

| `code` | 含义 | 实测 body |
| --- | --- | --- |
| `200` | 成功 | — |
| `401` | 未登录 / token 失效 | `{"msg":"请先登录！","code":401,"data":"SUMC_"}` |
| `500` | 业务失败，`msg` 可能是中文，**也可能是 i18n key** | `{"msg":"app_retrun_error_applogin","code":500}` |
| `501` | 前端拦截器按 401 同级处理（强制重登） | — |

前端拦截器原文逻辑：

```js
if (401 != A.data.code && 501 != A.data.code || /* getInfo / getIstoken 除外 */) {
  confirm("登录状态已过期…") → 清 Token/Identity/user/weakPass → 跳 #/login
}
```

`data` 在 401 时返回的是 **schoolKey**（`SUMC_`），不是错误详情。

### 1.4 静态资源 / 图片 / 附件

```text
图片/下载： GET /dev-api/download?filename=<img 文件名>
```
登录页 logo、首页 banner 都由 `getimage` / `getmainimage` 返回文件名后拼这个地址。

### 1.5 `schoolKey`

`SUMC_`（Shantou University Medical College）。服务端在未登录时也会随 401 一起返回，前端还会在 `getIstoken` 的 `data` 里拿到。部分逻辑对 `schoolKey` 做白名单分支（前端出现过 `SUMC_`、`JXUTCM_`、`GXMU_` 等，是同一产品的多校部署）。

## 2. 登录

### 2.1 完整流程（4 个请求）

```text
1) GET  /dev-api/appapi/getIstoken                       → 探活 + 拿 schoolKey
2) GET  /dev-api/appapi/getimage                         → 登录页背景图（可跳过）
3) GET  /dev-api/appapi/captcha/getCaptchaCode?yzmcode=  → 验证码图片
4) POST /dev-api/appapi/applogin                         → 拿 token
```

### 2.2 `GET /dev-api/appapi/getIstoken`

路由守卫每次跳转都会调它。

**实测（未登录）：**
```http
GET /dev-api/appapi/getIstoken HTTP/1.1
Host: jwgl.med.stu.edu.cn
```
```http
HTTP/1.1 200 OK
Content-Type: application/json; charset=utf-8

{"msg":"请先登录！","code":401,"data":"SUMC_"}
```

**已登录时（代码反推）**，前端判定 `code == 200` 后直接读 `schoolKey`：

```json
{ "code": 200, "schoolKey": "SUMC_" }
```

前端语义：`code==200` → 已登录，放行；否则拿 `data` 当 `schoolKey`，然后决定是否跳 `#/login`。

### 2.3 `GET /dev-api/appapi/captcha/getCaptchaCode?yzmcode=<毫秒时间戳>`

| 项 | 值 |
| --- | --- |
| 方法 | `GET` |
| 查询参数 | `yzmcode` = `Date.now()` 的**毫秒**值（如 `1793280939807`） |
| 不需要 token | 是（`isToken:false` 语境） |
| **实测响应头** | `HTTP/1.1 200 OK`，`Content-Type: image/jpeg; charset=UTF-8` |
| **实测响应体** | JPEG 位图，**120×40 px，约 1.9–2.0 KB** |
| Cookie | 服务端**不下发任何 Set-Cookie**；验证码完全是 **stateless** 的，靠 `yzmcode` 关联 |

前端拼 URL 的方式（注意这里没有 `/dev-api` 字面量，是 `downloadapi + "appapi/..."`）：

```js
restCaptcha(){
  this.yzmCode = (new Date).getTime();                       // 毫秒时间戳
  this.yzmImgUrl = this.$global.downloadapi                  // "/dev-api/"
                 + "appapi/captcha/getCaptchaCode?yzmcode=" + this.yzmCode;
}
```

> 因为 `yzmcode` 由**客户端**指定，服务端必须把它当作 key 存答案，所以每次登录都要**新取一张图**并把同一个时间戳原样放进 `yzmCode`。

### 2.4 `POST /dev-api/appapi/applogin`（核心）

```http
POST /dev-api/appapi/applogin HTTP/1.1
Host: jwgl.med.stu.edu.cn
Content-Type: application/json;charset=utf-8
Origin: https://jwgl.med.stu.edu.cn
Referer: https://jwgl.med.stu.edu.cn/app/index.html

{"username":"<账号>","password":"<RSA(Base64)>","code":"","appid":null,"yzmCode":1793280939807,"verifyCode":"<验证码>"}
```

**body 字段表**

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `username` | string | 是 | 学号 / 工号 / 账号（也接受身份证号，见错误文案） |
| `password` | string | 是 | **RSA-512 / PKCS#1 v1.5** 加密明文密码，输出 **Base64**，固定 **88 字符** |
| `code` | string | 是（可为 `""`） | CAS 回调的 `?code=`；本系统 `casEnable=false`，恒为 `""` |
| `appid` | string \| null | 可 | 极光推送 RegistrationID；H5 端为 `null` |
| `yzmCode` | number | 是 | **取验证码时用的那个毫秒时间戳**，必须一致 |
| `verifyCode` | string | 是 | 验证码图片里的字符（实测**大小写敏感性未验证**，见 §10） |

**前端原始提交代码：**

```js
async login(){
  localStorage.clear();
  const e = {
    username: this.account,
    password: jsencrypt_w(this.password),   // ← RSA 加密
    code: this.code,                        // ← 从 URL ?code= 取，无则 ""
    appid: this.bindform.appid,
    yzmCode: this.yzmCode,                  // ← 取图时的时间戳
    verifyCode: this.verifycode             // ← 用户输入的验证码
  };
  const t = await this.$ajax.post("/appapi/applogin", e);
  if (200 == t.code) {
    localStorage.setItem("weakPass", t.weakPass);
    localStorage.setItem("Token",    t.user.token);   // ← token 在这里
    localStorage.setItem("Identity", t.user.usertype);
    localStorage.setItem("user", JSON.stringify(t.user));
    ...
  }
}
```

**RSA 公钥（前端硬编码，全产品同一把，非机密）：**

```
MFwwDQYJKoZIhvcNAQEBBQADSwAwSAJBAKoR8mX0rGKLqzcWmOzbfj64K8ZIgOdH
nzkXSOVOZbFu/TJhZ7rFAN+eaGkl3C4buccQd/EjEsj9ir7ijT7h96MCAwEAAQ==
```

拆开是标准 **SubjectPublicKeyInfo / DER**，模长 **512 bit**，填充 **PKCS#1 v1.5**，输出 **Base64**。

**Node 参考实现（已实测可产出服务端可解析的密文）：**

```js
const c = require('crypto');
const k = 'MFwwDQYJKoZIhvcNAQEBBQADSwAwSAJBAKoR8mX0rGKLqzcWmOzbfj64K8ZIgOdHnzkXSOVOZbFu/TJhZ7rFAN+eaGkl3C4buccQd/EjEsj9ir7ijT7h96MCAwEAAQ==';
const pem = '-----BEGIN PUBLIC KEY-----\n' + k.match(/.{1,64}/g).join('\n') + '\n-----END PUBLIC KEY-----';
const cipher = c.publicEncrypt({ key: pem, padding: c.constants.RSA_PKCS1_PADDING },
                               Buffer.from(plainPassword)).toString('base64');
```

**Python 参考实现：**

```python
import base64
from Crypto.PublicKey import RSA
from Crypto.Cipher import PKCS1_v1_5

KEY = base64.b64decode(
    "MFwwDQYJKoZIhvcNAQEBBQADSwAwSAJBAKoR8mX0rGKLqzcWmOzbfj64K8ZIgOdH"
    "nzkXSOVOZbFu/TJhZ7rFAN+eaGkl3C4buccQd/EjEsj9ir7ijT7h96MCAwEAAQ=="
)
def enc(plain: str) -> str:
    pub = RSA.import_key(KEY)
    return base64.b64encode(PKCS1_v1_5.new(pub).encrypt(plain.encode())).decode()
```

> 输出长度校验：明文 ≤ 53 字节时密文恒 64 字节 → Base64 恒 88 字符。若你的实现给的不是 88 字符，加密就是错的。

**结论**：协议链路（含 RSA 加密、验证码绑定）已被实测打通到"凭据校验"这一步，失败点在于**该账号/密码在本系统被拒**。因此：

- 未取得 token → 下文所有"登录后的响应结构"均为**代码反推**，不是实测样例。
- 进一步自动化的唯一缺口是**图形验证码识别**（120×40 JPEG，4–5 字符，含一条贯穿全图的干扰斜线，字符间距粘连，人工/mo­del 目视识别准确率约 50–70%）。
- 已用的 3 次提交里，第 1、2 次的失败原因分别是验证码与过期，**不构成密码错误计数**；第 3 次才是真正的凭据校验。按"最多 5 次"的约束，**主动停止**，未继续试探。

## 3. 课表

### 3.1 `POST /dev-api/appapi/Studentkb/index`（主接口）

```http
POST /dev-api/appapi/Studentkb/index
token: <token>
Content-Type: application/json;charset=utf-8

{"zc":"all","jc":"","teadm":""}
```

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `zc` | string \| number | 周次。`"all"` = 全部周；否则为 `1..maxzc` 的整数（前端下拉就是 `all` + 每周） |
| `jc` | string | **时间段模式 id**。`""` = 默认全天模式；其他值来自同一响应里的 `modelist[].value`（例如分"上午/下午"两套作息） |
| `teadm` | string | 教师代码；**学生端恒传 `""`** |

> **注意**：此接口**没有学期参数**（前端只发 `zc/jc/teadm`）。即它只能取**当前学期**的课表，学期由服务端会话决定。想取别的学期只能靠后端默认学期切换（本系统未提供前端入口）→ 见 §10。

**响应（代码反推）**

```json
{
  "code": 200,
  "xnxqdm": "2026-2027-1",
  "firstDayOfWeek": "2026-08-31",
  "zc": 8,
  "curDay": 4,
  "stillWeek": 8,
  "rq": "2026-10-29",
  "minzc": 1,
  "maxzc": 20,
  "issj": true,
  "xldata": [ { "zc": 1, "qsrq": "2026-08-31", "jsrq": "2026-09-06" } ],
  "nodelist": [ { "jcdm": "0102", "jcmc": "第1-2节", "qssj": "08:00", "jssj": "09:40" } ],
  "modelist": [ { "text": "全天模式", "value": "" } ],
  "kbList": "[[...],[...],[...],[...],[...],[...],[...]]"
}
```

**关键：`kbList` 是 JSON 字符串，不是数组**，前端必须 `JSON.parse(a.kbList)`：

```js
var e = JSON.parse(a.kbList);
A.mondayList.push(e[0]);  A.TuesdayList.push(e[1]);  A.WednesdayList.push(e[2]);
A.ThursdayList.push(e[3]); A.FridayList.push(e[4]);  A.SaturdayList.push(e[5]);
A.SundayList.push(e[6]);
```

`JSON.parse(kbList)` 得到**长度 7 的数组**，索引 `0..6` = **周一…周日**，每个元素是该天的课程对象数组。

**顶层字段表**

| 字段 | 类型 | 含义 |
| --- | --- | --- |
| `code` | number | 200 成功 |
| `xnxqdm` | string | 学年学期代码 |
| `firstDayOfWeek` | string | 该学期**第一周周一**的日期（`YYYY-MM-DD`） |
| `zc` | number | **当前教学周**（服务端已算好） |
| `curDay` | number | 当前是周几 |
| `stillWeek` | number | 当前周（用于文案"第 N 周"） |
| `rq` | string | 服务器当前日期 `YYYY-MM-DD`（前端 `rq.substr(5,2)` 取月份） |
| `minzc` / `maxzc` | number | 周次下限/上限，用于生成周次下拉 |

### 7.2 学期起止 & 当前教学周怎么取

**结论：不需要本地推算**，服务端直接给：

| 需求 | 来源 |
| --- | --- |
| 学期起止 | `appxl/data` 的 `calendar` 首尾 `rqmc`；或 `appxl/index` 的 `xnxqList` + `Studentkb/index.xldata`（每周 `qsrq`/`jsrq`） |

| **当前教学周** | `Studentkb/index.zc`（还有 `stillWeek`、`curDay`、`rq`） |

如果要**脱离课表接口**单独算周次，用：

```
当前周 = floor((今天 - firstDayOfWeek) / 7) + 1
```

同域老门户（`/new/welcome.page`）里对应的是强智传统的 `getCurrentTime`（`app.do?method=getCurrentTime&currDate=`），但**本 host 的 `/app.do` 是 404**（见 §8），只能走 `appxl` + `Studentkb`。

## 8. 厂商归属 & 与主校区的关系（重点结论）

### 8.1 这是谁的产品

**强智科技（QIANZHI）新版"教学服务平台"**，`schoolKey = SUMC_`。

证据链（全部来自本次实测/拆包，不是猜）：

1. **同域并存老门户**：`https://jwgl.med.stu.edu.cn/new/welcome.page?ui=new` → **302**，跳 `sso.med.stu.edu.cn`，`service=https://jwgl.med.stu.edu.cn/new/ssoLogin`。`welcome.page` + `ssoLogin` 是**强智教务**老门户的固定形态。
2. **字段命名体系是强智的 pinyin 缩写**：`xnxqdm`（学年学期代码）、`jcdm`/`jcdm2`（节次代码）、`kcbh`（课程编号）、`xsbh`（学号）、`kcdlmc`（课程大类名称）、`cjfsdm`（成绩方式代码）、`dqszj`（所在级）、`rxnf`（入学年份）、`zxqjc`…。这套命名与公开的强智 `app.do?method=` 老 API 完全同源（对比 `getUserInfo` 返回的 `dqszj/rxnf/xz/yxmc/zymc`、`getCjcx` 返回的 `kcmc/kcywmc/zcj/xf`）。
3. **多校多租户**：`schoolKey` 形如 `SUMC_` / `JXUTCM_` / `GXMU_`，前端多处按 `schoolKey` 做差异分支（如 `"SUMC_"==schoolKey` 时隐藏学分、隐藏座位号、"重地"字段）。单品多校是强智的部署方式。
4. **新老两套面**：老面 `app.do?method=`（移动端 API，QZAPI/HUT_API 那一类）在本 host **404**；新面 `/appapi/...`（本产品）**存在**。说明这是**新版教学服务平台**，不是老移动端 API 的换皮。
5. webpack chunk 名 `entss_app`、localStorage 前缀 `ntss_`——产品内部代号，无对外意义，但和强智产品线的命名习惯一致。

> 客观说明：bundle 里**没有**"强智""qzdatasoft""QZDATASOFT"等字面厂商串（已全量 grep 0 命中），官网首页也被学校换成了自绘启动页，所以厂商标识是**由 1+2+3+4 的行为指纹推定**，不是读到厂名。

### 8.2 主校区 `jw.stu.edu.cn` 是不是同一套

**不是。厂商不同、协议不同。**

| | 医学院 `jwgl.med.stu.edu.cn` | 主校区 `jw.stu.edu.cn` |
| --- | --- | --- |
| 厂商 | 强智（新版教学服务平台） | **正方（ZFsoft）** |
| 路径特征 | `/app/index.html`、`/dev-api/appapi/`、`/new/welcome.page` | `/jsxsd/`（`/jsxsd/framework/xsMainV.htmlx`、`/jsxsd/xk/LoginToXk`）、`/jwglxt/xtgl/login_slogin.html` |

### 8.3 "把 stu-mcp 的 host 换成 jwgl.med.stu.edu.cn 就能用" —— **不成立**

四条独立理由，任一条都足以否掉：

1. **协议不同**：stu-mcp 的教务侧是**正方** `/jsxsd/...` + CAS Cookie 会话（`JW_PATHS` 里 5 条正方路径 + `cas.py` 的票据链）。医学院是**强智** `/dev-api/appapi/` + `token` 头 JSON-RPC 风格。改 host 只是把正方请求打到一个强智服务器上 → 全是 404 或 SSO 跳转。
2. **同一台机器上老强智 API 也不通**：`https://jwgl.med.stu.edu.cn/app.do?method=getCurrentTime&currDate=2026-10-29` → **404**；`app.do?method=getXnxq`、`getKbcxAzc` 同样 **404**。也就是说连"强智老 API 客户端"（QZAPI / HUT_API 那一类）换 host 都不行，只有 `appapi` 新面可用。
3. **登录完全不同**：医学院必须 `RSA-512(密码)` + 图形验证码（`yzmCode` 时间戳绑定，TTL 约 1–2 分钟）+ `POST /dev-api/appapi/applogin`；正方是表单 POST `/jsxsd/xk/LoginToXk` 或 CAS 票据。没有可复用的认证代码。
4. **代码事实**：在本工作区 `stu-mcp-reverse/repo` 的 244 个 `.py/.toml/.json/.yaml` 文件里 `app.do` 命中 **0**、`appapi` 命中 **0**、`getKbcxAzc` 命中 **0**、`authUser` 命中 **0**；`jwgl` 只出现在 `cas.py` / `service.py` / `capability_catalog.py` 的**域名白名单**里（当"另一个汕大教务主机"登记），没有任何 `appapi` 实现。

**反过来成立的表述**：

> 只要客户端本来就是按 `POST /dev-api/appapi/*` + 请求头 `token` 写的强智新版客户端，那么把 base 从别的强智学校的 host 换成 `jwgl.med.stu.edu.cn` **是可以用的**——但必须同时满足：① 路径前缀 `/dev-api/appapi/`；② 登录走 `applogin` 的 RSA+验证码；③ 请求头名是小写 `token`；④ 不同学校的 `schoolKey` 分支逻辑（本机是 `SUMC_`）要认。
> 若客户端是正方（`/jsxsd/`）写的，换 host 一定不可用。

### 8.4 如果要接主校区怎么办

主校区那条路要走 **CAS 票据换业务会话**：`sso.stu.edu.cn` 登录 → 带 `service=http://jw.stu.edu.cn/` 拿 ticket → 交回 jw.stu.edu.cn → 拿 Cookie → 再访问 `/jsxsd/...`。这与本文的 `appapi` 体系是两条完全独立的链路，**没有共用 token 的可能**。

### 关于验证码这件事的实操建议

如果要做无人值守客户端，只有三条路：

1. **人工读图**（本文的做法）：每次登录需要人看一张 120×40 图，成本高但 100% 可靠；TTL 约 1–2 分钟，取图后要**立刻**提交。
2. **接 OCR**：这家的图有贯穿全图的干扰斜线、字符粘连、字符集是大小写字母+数字混合。纯 `tesseract` 基本不可用；需要自建小模型或用付费打码平台（4–5 字符、字母数字混合，属于标准难度）。
3. **换 `jzapplogin`**：走短信验证码，`password` 明文、无图形码，但每次登录要收一条短信，且需要先有 `getsmsCode` 的短信通道权限。
