## 以后怎样登记

1. **产品版本**：只因实际产品功能、修复及交付需要调整 `web/android/app/build.gradle` 的 `defaultConfig`。`python deploy/sync-version.py --write` 只同步产品 Web 常量和 `backend/app/latest_version.json`；后者 `channel=product`，更新说明只写实际产品行为。
2. **完整 App 验证**：`Haptics` 保留完整业务、独立包名与构建证书。它验证产品功能，但不能代替正式签名及生产发布验收。
3. **机型探针**：版本独立登记在 `deploy/probe-versions.json`，通过 Android Components 覆盖探针输出。今后的实验只更新对应探针登记，例如增加 `-vivoidentity.2` 后缀及该包的 code，不修改产品三份版本文件。已交付的旧编号只是历史，不为整理制造一次新包或新功能版本。
4. **覆盖安装**：versionCode 下限按最终 applicationId 检查；结合登记的已确认交付下限和本机 APK 实际头信息，全新检出目录也不能忽略交付历史。打包脚本不会自动改写账本；新交付后依据真实回执更新 `lastDeliveredVersionCodes` 并单独提交登记，不能在交付前把候选 code 登记为已交付，否则会阻止自身打包。通用、华为与完整 App 不共用升级序列；Vivoprobe 和 Vivoidentity 使用同一包名，必须共用下限。高德实验身份仍与真实高德冲突，不能为测试要求卸载真实应用。
5. **GitHub**：产品 PR 标记 `product-change`，探针及其实测文档标记 `device-probe`，本次版本制度整理标记 `release-maintenance`。提交前缀优先 `test(probe)`、`docs(probe)`；保留旧提交 SHA。`.github/release.yml` 从自动产品发布说明排除后两类，发布前仍人工核对。
6. **发布状态**：正式发布应记录实际签名、包名、源码 SHA、版本、哈希与部署验收；只有真实发布后才创建相应产品 Release／标签。本次不发布 APK、不修改线上服务、不广播升级。

GitHub 发布说明过滤使用[官方配置](https://docs.github.com/en/repositories/releasing-projects-on-github/automatically-generated-release-notes)。APK、签名及原始设备日志继续留在忽略目录，只提交源码和必要的脱敏记录。
