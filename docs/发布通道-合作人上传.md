# 合作人上传 → 你批准 → 大脑发布：一条只传不发的通道

> 目标：合作人能把新版本交给服务器，但**碰不到服务器的任何东西**；只有你说「发」，
> 大脑才真正推上线。全程留审计。

---

## 一、三个角色，三种权限

| 角色 | 账号 | 能做什么 | 不能做什么 |
|---|---|---|---|
| **合作人** | `stuup` | 只能 SFTP 把文件放进 `/srv/stu-upload/inbox` | 不能登录 shell、不能跑命令、不能端口转发、不能看 inbox 以外任何地方 |
| **大脑** | `sturead-brain` | 读 inbox；用 `sudo stu-release` 校验、接收、发布、退回 | 除这一个脚本外，任何 root 命令都不给（`sudo id` 都会被拒） |
| **监管机** | `sturead-watch` | 只读 inbox（看有没有新包、看审计） | 不能写、不能发布 |

数据中心是唯一的落脚点；网页包由**大脑**发到静态站。

---

## 二、给合作人什么

一把专用密钥的公钥：

```
ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAICuIQ2wVHZAqkxwKUHOXnwRHmmumlnoUBA5tCRLOpGCJ stuup-release-upload
```

他这样上传：

```bash
# 单文件
sftp -i ~/.ssh/合作人私钥 stuup@<数据中心地址>
sftp> put stu-assistant-server.tar.gz
sftp> put STU事项助手-1.0.32.apk

# 或者一行命令
scp -i ~/.ssh/合作人私钥 发布包.tar.gz stuup@<数据中心地址>:
```

注意两点：

1. **登录后就在 `/inbox` 里**，直接 `put 文件名` 即可，别写 `inbox/xxx`（会变成 `inbox/inbox/xxx`）。
2. 他只能看到 `/inbox`、`/accepted`、`/rejected` 三个目录名；`/accepted` 里有什么他看不到（没有读权限）。

包有两种合法形态：

| 类型 | 要求 |
|---|---|
| 服务器包 | `*.tar.gz`，里面有 `stu-assistant-server/backend/app/main.py` 和 `deploy/install.sh` |
| 网页包 | `*.tar.gz`，里面有 `index.html` |
| 安装包 | `*.apk`，> 1 MB 且是合法 zip |

> 不许绝对路径、不许 `..`；单文件上限 200 MB。

## 三、你要做的事：口头批准

合作人上传后会跟你说一句。你只需要判断「发」还是「不发」。

## 四、大脑要做的（一条命令）

```bash
ssh <数据中心别名>
sudo -u sturead-brain sudo stu-release list      # 看有什么新包
```

**批准后发布**（脚本自己识别类型）：

```bash
sudo -u sturead-brain sudo stu-release deploy 文件名.tar.gz
```

它做的事，按顺序：

1. **校验**：tar 能否解开、有没有危险路径、包里该有的东西在不在；不过就什么都不改；
2. **留痕**：包进 `accepted/`，审计日志写一行；
3. **备份**：服务器包先把 `/opt/stu-assistant` 拷到 `/var/backups/stu-assistant/<时间>/`；
4. **发布**：
   - 服务器包 → 跑 `install.sh --no-proxy` → 检查 `stu-assistant` 服务活着；
   - 网页包 → 传到静态站的临时目录 → **保留旧的 `download/`（APK）** → 原子切换；
   - APK → 只放进 `/opt/stu-web/download/stu-assistant.apk`；
5. **自检**：打印首页 / APK / 版本探针的 HTTP 码；
6. **清 inbox**：成功才删 inbox 里那份。

**不批准**就退回：

```bash
sudo -u sturead-brain sudo stu-release reject 文件名.tar.gz 版本号不对
```

**只看不发**：

```bash
sudo -u sturead-brain sudo stu-release accept 文件名.tar.gz   # 校验+收进 accepted，不动生产
sudo -u sturead-brain sudo stu-release log 50                 # 审计日志
```

## 五、审计长什么样

```
/var/log/stu-release.log

2026-10-30T14:30:40+08:00 | sturead-brain | accept | webtest.tar.gz | ok | 207879 bytes
2026-10-30T14:33:46+08:00 | sturead-brain | deploy | webtest.tar.gz | ok | web
```

格式：`时间 | 操作者 | 动作 | 文件 | 结果 | 细节`。

## 六、已经验证过的边界

| 尝试 | 结果 |
|---|---|
| `ssh stuup@... id` | `This service allows sftp connections only.` |
| `sftp` 里 `cd /etc` | `No such file or directory`（chroot 关在 `/srv/stu-upload`） |
| `sftp` 里 `ls /` | 只能看到 `accepted` / `inbox` / `rejected` |
| `sftp` 里 `ls /accepted` | 空（没有读权限） |
| `sturead-brain` 跑 `sudo id` | `sudo: a password is required`（不在白名单） |
| `sturead-brain` 跑 `sudo sh -c id` | 同上，被拒 |
| `stu-release deploy ../../etc/passwd` | `inbox 和 accepted 里都没有：../../etc/passwd` |
| `sturead-watch` 写 inbox | `Permission denied` |

## 七、踩过的坑（改之前先看）

1. **chroot 目录必须 755 且 root 所有**。给 750 会让 sshd 在 chroot 之前读 `authorized_keys` 就被挡，报 `Could not open user 'stuup' authorized keys: Permission denied`。
2. **`tar | grep -q` 在 `set -o pipefail` 下永远判假**。grep 命中即退出，tar 收 SIGPIPE，整条管道非零。必须先 `listing=$(tar -tzf ...)` 再匹配。
3. **发网页包会把 APK 弄丢**。网页包里通常没有 `download/`，原子切换时旧目录一起没了，学生点下载就 404。脚本现在会先把旧 `download/` 搬进新目录，并自检 APK 的 HTTP 码。
4. **root 没有静态站的 ssh 别名**。给 `/root/.ssh/config` 单独配了 `web-host` 条目，用 `/root/.ssh/stu_deploy` 这把专用密钥（公钥已装到静态站）。
5. **上传路径别写 `inbox/`**。`ForceCommand internal-sftp -d /inbox` 已经把落脚点设在 inbox，再写一次会变成 `inbox/inbox/`。

## 八、相关文件

| 路径 | 作用 |
|---|---|
| `/usr/local/sbin/stu-release` | 发布脚本本体（仓库里是 `deploy/stu-release`） |
| `/etc/sudoers.d/stu-release-brain` | 只给 `sturead-brain` 这一条 |
| `/srv/stu-upload/inbox` | 合作人可写 |
| `/srv/stu-upload/accepted` | 校验通过的包（合作人看不到） |
| `/srv/stu-upload/rejected` | 退回的包 |
| `/var/log/stu-release.log` | 审计 |
| `/var/backups/stu-assistant/` | 每次服务器包发布前的备份 |
| `/etc/ssh/sshd_config` 末尾 `Match User stuup` | 通道的锁 |
